# The Evolution of Todo: Spec-Driven Development & Cloud-Native AI Constitution

## Mission Statement

**Vision**: Transform developers from "syntax writers" to "system architects" through AI-native, spec-driven development.

**Purpose**: This constitution governs the development of a 5-phase evolutionary journey that takes a simple Todo application and transforms it into a distributed, AI-powered, cloud-native system. Every line of code is generated by AI agents following a rigorous specification-first methodology.

**Core Philosophy**:
- Specifications are the source of truth, not code
- AI agents are the implementers, humans are the architects
- Progressive complexity reveals cloud-native patterns naturally
- Every phase builds upon and extends the previous phase

---

## I. The Nine Pillars of AI-Driven Development

### 1. Specification-First Engineering
**Definition**: No code exists before its specification is complete and approved.

**Application in This Project**:
- Every feature starts with a `speckit.specify.md` document
- Requirements must be explicit, testable, and complete
- Acceptance criteria defined before implementation begins
- AI agents are blocked from coding until spec approval

### 2. Declarative Architecture
**Definition**: System design expressed through declarative artifacts, not imperative instructions.

**Application in This Project**:
- `speckit.plan.md` defines WHAT the system does, not HOW it's coded
- Component diagrams, API contracts, and data flows precede implementation
- Infrastructure-as-Code (Helm charts, K8s manifests) follows the same principle
- AI agents translate declarative plans into imperative code

### 3. Progressive Elaboration
**Definition**: Complexity introduced incrementally across phases, not all at once.

**Application in This Project**:
- Phase I: In-memory simplicity
- Phase II: Persistence and web interfaces
- Phase III: AI integration and natural language
- Phase IV: Containerization and orchestration
- Phase V: Distribution, events, and cloud deployment

### 4. AI-Agent Autonomy
**Definition**: AI agents execute implementation autonomously within constitutional boundaries.

**Application in This Project**:
- Claude Code generates all production code
- Humans refine specifications, not code
- Agents follow the Constitution → Specify → Plan → Tasks → Implement loop
- Manual coding is prohibited; spec refinement is the human contribution

### 5. Type Safety as Contract
**Definition**: All interfaces, data structures, and boundaries are statically typed.

**Application in This Project**:
- Python: Pydantic models, type hints on all functions
- TypeScript: Strict mode, no `any` types
- Database: SQLModel schemas with full type coverage
- API contracts: OpenAPI/JSON Schema validation

### 6. Test-Driven Validation
**Definition**: Tests are written before implementation and define success criteria.

**Application in This Project**:
- Every task includes test cases in `speckit.tasks.md`
- Red-Green-Refactor cycle enforced
- Unit tests for business logic, integration tests for APIs
- AI agents run tests to verify their own implementations

### 7. Event-Driven Thinking
**Definition**: Systems communicate through events, not direct calls.

**Application in This Project**:
- Phase V introduces Kafka/Dapr for event streaming
- Task events, reminders, and notifications flow through topics
- Microservices are decoupled through pub/sub patterns
- Eventual consistency embraced over distributed transactions

### 8. Cloud-Native by Design
**Definition**: Applications built for containerized, orchestrated, distributed environments.

**Application in This Project**:
- Phase IV: Docker, Helm, Kubernetes foundation
- Phase V: Dapr sidecars, horizontal scaling, service mesh patterns
- Stateless services, externalized configuration
- 12-factor app principles applied throughout

### 9. Reusable Intelligence
**Definition**: Solutions are captured as reusable patterns, skills, and blueprints.

**Application in This Project**:
- Claude Code Skills for common workflows
- MCP servers as reusable tool interfaces
- Helm charts as deployment blueprints
- Constitution itself is the reusable governance artifact

## II. Spec-Driven Development (SDD) Protocol

### The Immutable Workflow

**RULE**: AI agents MUST follow this sequence for every feature:

```
Constitution → Specify → Plan → Tasks → Implement → Validate
```

**Step-by-Step Execution**:

1. **Constitution Check**
   - Agent reads this document before any work
   - Identifies which principles apply to the current task
   - Verifies tech stack alignment

2. **Specify Phase**
   - Agent generates or updates `speckit.specify.md`
   - Includes: User journeys, requirements, acceptance criteria
   - Validates completeness: Can this be implemented without assumptions?
   - **GATE**: Human approval required before proceeding

3. **Plan Phase**
   - Agent generates `speckit.plan.md` from approved spec
   - Includes: Component breakdown, API contracts, data schemas
   - Defines technical approach, not implementation details
   - **GATE**: Architecture review before proceeding

4. **Tasks Phase**
   - Agent generates `speckit.tasks.md` breaking plan into atomic units
   - Each task: ID, description, preconditions, outputs, test cases
   - Tasks are dependency-ordered and independently testable
   - **GATE**: Task checklist approved before coding

5. **Implement Phase**
   - Agent writes code ONLY for approved tasks
   - Every code file references its Task ID and Spec section
   - Code must pass all test cases defined in tasks
   - **GATE**: Automated tests + human review

6. **Validate Phase**
   - Verify all acceptance criteria met
   - Run full test suite
   - Check compliance with constitution principles
   - **GATE**: Sign-off before phase completion

### Prohibited Agent Behaviors

AI agents MUST NOT:
- Generate code without a referenced Task ID
- Modify architecture without updating `speckit.plan.md`
- Propose features without updating `speckit.specify.md`
- Infer missing requirements (must request clarification)
- Bypass test-first discipline
- Introduce technologies outside the approved stack

### Conflict Resolution Hierarchy

When conflicts arise, this hierarchy applies:

1. **Constitution** (this document) - highest authority
2. **speckit.specify.md** (WHAT) - requirements truth
3. **speckit.plan.md** (HOW) - architecture truth
4. **speckit.tasks.md** (breakdown) - implementation truth

## IV. Architectural Patterns

### Model Context Protocol (MCP) Pattern

**Definition**: AI agents interact with applications through standardized tool interfaces.

**Implementation Requirements**:
- Phase III introduces MCP server with task operation tools
- Tools must be stateless (state stored in database)
- Each tool: clear purpose, typed inputs/outputs, error handling
- OpenAI Agents SDK calls MCP tools, not direct database access

**Mandatory MCP Tools** (Phase III+):

| Tool | Purpose | Parameters | Returns |
|------|---------|------------|---------|
| `add_task` | Create a new task | user_id (required), title (required), description (optional) | task_id, status, title |
| `list_tasks` | Retrieve tasks from the list | user_id (required), status (optional: "all", "pending", "completed") | Array of task objects |
| `complete_task` | Mark a task as complete | user_id (required), task_id (required) | task_id, status, title |
| `delete_task` | Remove a task from the list | user_id (required), task_id (required) | task_id, status, title |
| `update_task` | Modify task title or description | user_id (required), task_id (required), title (optional), description (optional) | task_id, status, title |

**Agent Behavior Specification**:

| Behavior | Description |
|----------|-------------|
| Task Creation | When user mentions adding/creating/remembering something, use add_task |
| Task Listing | When user asks to see/show/list tasks, use list_tasks with appropriate filter |
| Task Completion | When user says done/complete/finished, use complete_task |
| Task Deletion | When user says delete/remove/cancel, use delete_task |
| Task Update | When user says change/update/rename, use update_task |
| Confirmation | Always confirm actions with friendly response |
| Error Handling | Gracefully handle task not found and other errors |

### Action-Server-Node Pattern

**Definition**: Separation of logic (Action), API (Server), and execution environment (Node).

**Implementation in This Project**:
- **Action**: MCP tools, business logic functions
- **Server**: FastAPI endpoints, routing, validation
- **Node**: Container running the server (Docker/K8s)

**Responsibilities**:
- Actions: Pure functions, testable in isolation
- Server: HTTP handling, authentication, serialization
- Node: Deployment, scaling, health checks

### Stateless Service Pattern

**Requirement**: All services MUST be stateless.

**Implementation**:
- No in-memory session storage (use database or Redis)
- Conversation state stored in PostgreSQL (Phase III)
- JWT tokens for authentication (no server-side sessions)
- Horizontal scaling enabled by statelessness

**Validation**: Agent must demonstrate restart resilience (server restart doesn't lose state).

**Stateless Chat Request Cycle (Phase III)**:
1. Receive user message
2. Fetch conversation history from database
3. Build message array for agent (history + new message)
4. Store user message in database
5. Run agent with MCP tools
6. Agent invokes appropriate MCP tool(s)
7. Store assistant response in database
8. Return response to client
9. Server holds NO state (ready for next request)

## V. Infrastructure & Cloud Standards

### Containerization (Phase IV+)

**Container Runtime**: Docker

**Image Requirements**:
- Multi-stage builds for size optimization
- Non-root user in containers
- Health checks defined in Dockerfile
- Minimal base images (alpine or distroless)

**Registry**: Docker Hub or cloud provider registry

**AI Assistance**: Docker AI (Gordon) for intelligent operations

### Kubernetes Standards

**Local Environment**: Minikube (Phase IV)

**Cloud Environment**: Azure AKS, Google Cloud GKE, or Oracle OKE (Phase V)

**Manifest Management**:
- Helm charts for all deployments
- Values files for environment-specific config
- ConfigMaps for non-sensitive configuration
- Secrets for API keys, database credentials

**Resource Limits**:
- Every pod must have resource requests and limits
- No unbounded resource usage
- HPA (Horizontal Pod Autoscaler) for scalable services

**AI Assistance**:
- kubectl-ai for intelligent K8s operations
- kagent for cluster analysis and optimization

### Dapr Integration (Phase V)

**Requirement**: Use Dapr for distributed application runtime.

**Mandatory Building Blocks**:
1. **Pub/Sub**: Kafka abstraction for event streaming
2. **State Management**: Conversation and task state storage
3. **Service Invocation**: Inter-service communication
4. **Jobs API**: Scheduled reminders (preferred over cron)
5. **Secrets Management**: API keys and credentials

**Dapr Components**:
- `kafka-pubsub`: Event streaming
- `statestore`: PostgreSQL state store
- `kubernetes-secrets`: Secret store

**Benefits Enforced**:
- Swap Kafka for RabbitMQ with config change, not code change
- Multi-cloud portability
- Built-in retries and circuit breakers

### Event-Driven Architecture (Phase V)

**Message Broker**: Kafka (self-hosted via Strimzi) or Redpanda Cloud

**Topics Required**:
- `task-events`: All CRUD operations
- `reminders`: Scheduled reminder triggers
- `task-updates`: Real-time client sync

**Event Schema**:
- Every event must include: `event_type`, `task_id`, `user_id`, `timestamp`
- JSON serialization
- Versioned event schemas

**Consumer Patterns**:
- Recurring Task Service: Consumes task-events, creates next occurrence
- Notification Service: Consumes reminders, sends notifications
- Audit Service: Consumes all events, maintains history

### Code Quality

**PRINCIPLE**: 100% functional, original code. Zero plagiarism.

**Requirements**:
- AI agents generate code from specifications, not copy-paste
- All code must map back to a spec section and task ID
- Code comments explain WHY, not WHAT (code is self-documenting)

**Verification**:
- Plagiarism checks via code similarity tools
- Code review verifies spec traceability
- AI agent must cite spec when generating code

### Type Safety

**PRINCIPLE**: 100% type coverage.

**Python**:
- `mypy --strict` passes with no errors
- All public functions have type hints
- Pydantic models for all data

**TypeScript**:
- `tsc --strict` passes with no errors
- No `any` types
- All API responses typed

### Testing Standards

**Coverage Requirement**: 90%+ code coverage minimum

**Test Categories**:
1. **Unit Tests**: Business logic, pure functions
2. **Integration Tests**: API endpoints, database operations
3. **E2E Tests**: Critical user journeys (optional but encouraged)

**Test-First Discipline**:
- Tests written in `speckit.tasks.md` before implementation
- Red-Green-Refactor cycle enforced
- AI agent runs tests to verify its own code

### Security Standards

**Authentication**:
- Better Auth with JWT tokens
- Token expiry: 7 days max
- Refresh token rotation

**Authorization**:
- Every API endpoint validates user identity

- Passwords hashed with bcrypt

**Vulnerability Scanning**:
